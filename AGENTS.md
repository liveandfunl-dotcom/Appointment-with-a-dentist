# AGENTS.md

## Project

Система записи пациентов на приём к врачу. Внутренняя система клиники, без доступа в интернет.

- **Frontend** — React 19.3 + Vite, только CSR (SSR не нужен). Линтер: ESLint + TypeScript.
- **Backend** — NestJS 12.6. Линтер: ESLint + TypeScript.
- **БД** — SQLite (встроенный в Node.js). Клиника небольшая — выбрано для простоты администрирования и развёртывания.
- **Развёртывание** — Docker. Файл БД лежит во внешней папке (volume). Обновление frontend и backend — переустановкой контейнера; БД при этом сохраняется.
- **Тесты** — e2e: Playwright; unit: Jest.

### Структура

| Папка | Назначение |
|-------|------------|
| `frontend/` | клиентское приложение (React + Vite) |
| `backend/` | серверное приложение (NestJS) |

### Формат плана `docs/plans/<фича>.md`

- **Цель** — что и зачем делаем.
- **Границы** — что входит и что явно не входит.
- **Затрагиваемые файлы.**
- **Критерии приёмки** с постоянными AC-ID в формате `AC-<FEATURE>-<NN>` (например, `AC-AUTH-01`). ID не переиспользуются и не перенумеровываются. Критерии можно вместо плана добавить в соответствующую спеку в `docs/specs/`.

## Порядок разработки

Для любой нетривиальной фичи или изменения поведения действуй строго по порядку.
Не переходи к следующему шагу, пока не завершён предыдущий.

1. **План.** Сначала напиши план в `docs/plans/<фича>.md`: цель, границы, затрагиваемые файлы и критерии приёмки с постоянными AC-ID (или добавь их в соответствующую спеку в `docs/specs/`). После этого остановись и дождись одобрения.
2. **Тесты.** До написания реализации напиши тесты, которые проверяют критерии приёмки. Называй каждый тест по его AC-ID. Запусти их и убедись, что они падают по правильной причине. Покажи вывод с падением.
3. **Код.** Напиши минимум кода, чтобы тесты прошли. Не меняй тесты, чтобы они прошли. Если считаешь, что тест неверный, скажи об этом и спроси.
4. **Документация.** Преврати план в `docs/impl/<фича>.md`, удали файл плана, обнови таблицу «Start here» и `docs/impl/README.md`.

### Правила

- Не пиши код реализации, если нет одобренного плана и падающего теста.
- Мелкие правки (опечатка, правка текста, исправление в одну строку) могут пропускать шаги 1–2. В этом случае прямо скажи, что пропускаешь.
- Исправление бага начинай с падающего теста, который воспроизводит баг.
- Честно сообщай результаты тестов: если тест упал или был пропущен, так и скажи.
- Не делай коммиты, пока об этом явно не попросят.
