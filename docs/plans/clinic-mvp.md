# План: система записи пациентов к стоматологу (MVP)

## Context

Репозиторий пустой: есть только структура папок и правила в `AGENTS.md`. Нужно с нуля сделать SPA для записи к врачу в небольшой клинике. Описание задачи лежит в `описание проекта/prject.md`, модель БД — в `описание проекта/структура БД.md`, лимиты запросов — в `описание проекта/email.md`.

Стек задан в AGENTS.md: React 19.3 + Vite (CSR), NestJS 12.6, SQLite из `node:sqlite` (Node 24), Jest, Playwright, Docker. Если указанных версий нет в npm, берём последние доступные и сообщаем об этом.

Порядок работы: сначала тесты, потом код. Каждую подзадачу делает отдельный субагент, а готовые подзадачи отмечаются в файле плана.

План одобрен пользователем 2026-11-26 (шаг 1 из AGENTS.md). Готовые подзадачи отмечаются `[x]` с датой в разделе «Подзадачи».

## Принятые уточнения (по ответам пользователя)

| Вопрос | Решение |
|---|---|
| Как добавить администратора | В форме «Добавить врача» root видит выбор роли «Врач / Администратор». Для администратора скрыты специализация, кабинет, дни и время. Администраторы показываются в «Карточках врачей» только root и помечены ролью |
| Логин и пароль | В форме добавления и редактирования есть необязательные поля «Логин» и «Пароль». Без них пользователь входит только по magic link. Пароль хранится в виде хеша (scrypt) |
| Длина записи | От 1 часа, шаг 30 минут, запись занимает несколько смежных слотов. В `Appointments` добавляется `endDate` |
| Шаг времени | 30 минут: 00:00, 00:30 … 24:00. Время окончания должно быть больше времени начала (в описании условие записано наоборот, это опечатка) |
| Отмена записи | Кнопка «Отменить» в таблице на странице «Записи» у будущих активных записей, с попапом подтверждения. Запись не удаляется, а получает статус `cancelled`, и её слот снова свободен |
| Что видит врач | На странице «Записи» — только свои записи. Отменяет только свои будущие. Записывает пациентов только к себе |
| Кабинет и пациент | В форму врача добавляется поле «Кабинет». В таблице «Записи» дополнительно показываются имя и телефон пациента |
| «Форма записи» из меню | Если слот не выбран, показывается подсказка «Сначала выберите врача, дату и время» и ссылка на «Запись на приём» |
| Гость | Без входа доступны «Карточки врачей» (только просмотр) и страница входа. Остальные страницы ведут на `/login` |
| Rate limit | На оба маршрута входа: 5 запросов за 15 минут на один email или логин и 20 за 15 минут на один IP. Иначе ответ 429. Абзац про Tailscale в `email.md` к проекту не относится |
| Root | Логин `root`, пароль `root1234` («roor» в описании — опечатка), email `root@clinic.local` |
| Язык | По умолчанию RU, выбор языка хранится в localStorage. Коды языков: `ru`, `en`, `el` (в интерфейсе подпись «GR»). Письма уходят на языке интерфейса того, кто выполнил действие. Переводы лежат в json на фронте и на бэке |
| Почта | В dev и e2e используется Mailpit в docker-compose. В API-тестах — транспорт `memory` с перехватом писем. В рабочей среде SMTP настраивается через env |
| Часовой пояс | `CLINIC_TZ`, по умолчанию `Europe/Athens`. В БД время хранится в Unix seconds. API принимает и отдаёт дату и время в часовом поясе клиники строками `YYYY-MM-DD` и `HH:mm` |

Чего описание не уточняет и что я решил сам:
- Окна для записи показываются в правом столбце, потому что левый занят списком и календарём.
- Деактивированный пользователь не может войти, его сессии удаляются.
- Admin и root видят в карточках деактивированных врачей с пометкой, иначе их нельзя было бы снова активировать. Гость и врач видят только активных.
- Admin управляет только врачами. Root управляет врачами и админами. Самого root через API изменить нельзя.
- Второй кнопкой в режиме входа по логину и паролю будет «Войти по email» — она возвращает к форме с email.

Сознательно не входит в MVP: регистрация пациентов, отчёты, напоминания пациентам, редактирование уже созданной записи, перенос записи, HTTPS и прод-харднинг.

## Архитектура

- **Монорепо на npm workspaces.** Корневой `package.json` объединяет `backend`, `frontend` и `tests`. Общий ESLint с TypeScript.
- **Backend** (`backend/src`):
  - `app.factory.ts` экспортирует `createApp({ dbPath, now?: () => Date, mail: 'smtp'|'memory', seedDev?: boolean })`. Функция нужна, чтобы API-тесты поднимали приложение в своём процессе.
  - Модули:
    - `db`: обёртка над `DatabaseSync`, раннер миграций (таблица `schema_migrations`), сиды.
    - `clock`: провайдер `Clock`, в тестах подменяется.
    - `auth`: сессии, magic link, логин, guard'ы ролей, in-memory rate limiter.
    - `users`.
    - `appointments`: записи и свободные окна.
    - `mail`: nodemailer. `MailService.outbox` хранит письма при `mail: 'memory'`. Шаблоны писем — в `backend/src/i18n/{ru,en,el}.json`.
  - Время в часовом поясе считается через `luxon`.
  - В Docker backend раздаёт и статику фронтенда.
- **Сессия.** Cookie `session`: httpOnly, SameSite=Lax, срок 30 дней. В БД хранится хеш токена (sha256).
- **Frontend** (`frontend/src`):
  - React Router.
  - `api/client.ts`: fetch с `credentials: 'include'`, ошибки по кодам.
  - `AuthContext`.
  - i18n на `react-i18next`, переводы в `src/i18n/{ru,en,el}.json`.
  - Компоненты:
    - `Header`, `LanguageSelect`, `ConfirmDialog`.
    - `DatePicker`: переиспользуемый, неделя начинается с понедельника, принимает `isDateDisabled`, названия месяцев и дней локализованы.
    - `TimeSelect`.
  - Страницы: `RecordsPage`, `BookingPage`, `BookingFormPage`, `DoctorsPage`, `DoctorFormPage` (добавление и редактирование), `LoginPage`, `MagicLinkPage`.
  - Выбранный на `BookingPage` слот передаётся в форму через state роутера.
  - Стили — обычный CSS по БЭМ, по файлу на блок. Токены задаются в `styles/tokens.css`: тёплая палитра (кремовый фон `#FFF7EE`, акценты персиковый и терракотовый), тёмные цвета только у текста, поля со скруглением 6px, label над полем, отступ между полями 16px.
  - Vite проксирует `/api` на backend.
- **Модель данных** (расширение `структура БД.md`):
  - `Users`: поля из описания плюс `specialization`, `phone`, `workDays` (TEXT, например `"1,2,3,4,5"`, где 1 — понедельник), `workStart` и `workEnd` (минуты 0–1440, кратно 30), `createDate`. Поле `pass` хранит хеш. `email` и `login` уникальны (`login` может быть NULL). Ровно один из флагов `isRoot`, `isAdmin`, `isDoctor` равен 1.
  - `Appointments`: поля из описания плюс `endDate`, `patientName`, `patientPhone`, `comment`, `status` (`active`/`cancelled`), `cancelDate`, `cancelerId`.
  - Новые таблицы: `MagicLinks` (`tokenHash`, `userId`, `expiresAt`, `usedAt`), `Sessions` (`tokenHash`, `userId`, `expiresAt`, `createDate`).
- **API.** Все пути начинаются с `/api`. Ошибки приходят в виде `{ code, fields? }`.
  - Авторизация:
    - `POST auth/magic-link` `{email, lang}`
    - `POST auth/magic-link/verify` `{token}`
    - `POST auth/login` `{login, password}`
    - `POST auth/logout`
    - `GET auth/me`
  - Пользователи:
    - `GET users` — карточки, состав зависит от роли.
    - `GET users/:id`, `POST users`, `PATCH users/:id` — только admin и root.
  - Записи:
    - `GET doctors/:id/free-windows?date=`
    - `GET appointments?date=&doctorId=`
    - `POST appointments` `{doctorId, date, start, end, patientName, patientPhone, comment?, lang}`
    - `POST appointments/:id/cancel`
- **Docker.**
  - `build/Dockerfile`: multi-stage сборка, один образ для frontend и backend.
  - `build/docker-compose.yml`: сервисы `app` и `mailpit`, volume `./data:/data`, `DB_PATH=/data/clinic.db`.
  - Миграции и сид root выполняются при каждом старте и не создают дублей.
  - Переменные окружения: `SMTP_HOST/PORT/USER/PASS/FROM`, `APP_URL`, `CLINIC_TZ`, `DB_PATH`, `SEED_DEV`, `PORT`.
- **Dev-сид** (при `SEED_DEV=true`):
  - 5 врачей: `doctor1..5@clinic.local`, логины `doctor1..5`, пароль `doctor1234`. У врачей разные специализации, кабинеты и графики.
  - 1 администратор: `admin@clinic.local`, логин `admin`, пароль `admin1234`.

## Критерии приёмки

**AUTH**
- AC-AUTH-01: magic-link для существующего активного email отвечает 200, и на этот email уходит письмо со ссылкой `APP_URL/auth/magic?token=…` на языке `lang`.
- AC-AUTH-02: для неизвестного или деактивированного email ответ 404 `USER_NOT_FOUND`, письмо не отправляется.
- AC-AUTH-03: verify с действующим токеном отвечает 200 и ставит httpOnly cookie на 30 дней.
- AC-AUTH-04: токен старше 30 минут → 401 `LINK_EXPIRED`.
- AC-AUTH-05: повторно использованный токен → 401.
- AC-AUTH-06: login с верным логином и паролем отвечает 200 и ставит cookie. Пара `root`/`root1234` работает.
- AC-AUTH-07: неверный пароль, неизвестный логин или деактивированный пользователь → 401 `INVALID_CREDENTIALS`.
- AC-AUTH-08: `me` с cookie возвращает `{id, surname, name, role}`, без cookie → 401.
- AC-AUTH-09: через 30 дней сессия истекает, ответ 401.
- AC-AUTH-10: после logout сессия недействительна.
- AC-AUTH-11: rate limit на magic-link: больше 5 запросов за 15 минут на один email или больше 20 на один IP → 429.
- AC-AUTH-12: такой же rate limit на login, с подсчётом по логину и по IP.
- AC-AUTH-13: при деактивации пользователя все его сессии завершаются.

**DB**
- AC-DB-01: при первом старте создаётся схема и пользователь root. Перезапуск не создаёт дублей.
- AC-DB-02: при `SEED_DEV=true` создаются 5 врачей и 1 администратор, повторный запуск ничего не дублирует.
- AC-DB-03: пароли хранятся в виде хеша.
- AC-DB-04: миграции применяются к существующей БД без потери данных.

**USERS**
- AC-USERS-01: гость и врач получают в `GET users` только активных врачей с полями ФИ, специализация, телефон, email, дни, начало и конец работы, кабинет. Без login и pass.
- AC-USERS-02: admin дополнительно видит деактивированных врачей с `isActive`. Root видит ещё и админов с `role`.
- AC-USERS-03: admin создаёт врача → 201. Если не заполнены обязательные поля или неверен email → 400 `VALIDATION_ERROR` со списком полей.
- AC-USERS-04: `workStart >= workEnd`, время не кратно 30 минутам, время вне 0–1440 или не выбран ни один день → 400.
- AC-USERS-05: email или логин уже заняты → 409.
- AC-USERS-06: admin не может создать админа (403). Root может, при этом поля врача не требуются.
- AC-USERS-07: врач получает 403 на создание и изменение, гость — 401.
- AC-USERS-08: PATCH меняет любые поля. Пустой пароль оставляет старый. Новым паролем можно войти.
- AC-USERS-09: PATCH `isActive=false` деактивирует пользователя: он не может войти, записать к нему нельзя. `isActive=true` возвращает доступ.
- AC-USERS-10: admin не может менять админов и root (403). Root может менять админов.
- AC-USERS-11: `GET users/:id` для admin и root возвращает все данные, включая login, без пароля.

**SLOTS**
- AC-SLOTS-01: free-windows возвращает свободные окна длиной от 60 минут в рабочее время врача. Активные записи окна занимают, отменённые — нет.
- AC-SLOTS-02: в нерабочий день ответ `[]`.
- AC-SLOTS-03: прошедшие даты дают `[]`. Сегодняшние окна начинаются не раньше ближайшей будущей отметки, кратной 30 минутам.
- AC-SLOTS-04: для деактивированного врача → 404, для гостя → 401.

**APPT**
- AC-APPT-01: admin и root записывают пациента к любому активному врачу → 201. Заполняются `createDate` и `creatorId`.
- AC-APPT-02: врач записывает только к себе, к другому врачу → 403.
- AC-APPT-03: имя и телефон пациента обязательны, комментарий нет. Длительность не меньше 60 минут, начало и конец кратны 30 минутам. Иначе 400.
- AC-APPT-04: запись вне рабочего дня или часов, в прошлом или к деактивированному врачу → 400 `SLOT_UNAVAILABLE`.
- AC-APPT-05: пересечение с активной записью → 409 `SLOT_TAKEN`.
- AC-APPT-06: `GET appointments?date` для admin и root возвращает записи всех врачей или одного (`doctorId`), отсортированные по началу. Поля: start, end, ФИ врача, кабинет, patientName, patientPhone, status, canCancel.
- AC-APPT-07: врач всегда получает только свои записи.
- AC-APPT-08: admin и root отменяют любую будущую запись → status `cancelled`, слот освобождается.
- AC-APPT-09: отмена прошедшей или текущей записи → 400 `NOT_CANCELLABLE`.
- AC-APPT-10: врач отменяет свою будущую запись (200), чужую — 403.
- AC-APPT-11: гость получает 401 на всех маршрутах записей.

**MAIL**
- AC-MAIL-01: после создания записи врач получает письмо «На приём записан {пациент}, {дата} {начало}–{конец}. Контактный телефон: {телефон}» на ru, en или el.
- AC-MAIL-02: если SMTP недоступен, запись всё равно сохраняется, в ответе `mailSent: false`.

**UI** (тесты фронтенда: Jest + RTL и Playwright)
- AC-UI-HEADER-01: на всех страницах есть шапка: горизонтальное меню, выбор языка, кнопка «Войти» или «Выйти».
- AC-UI-HEADER-02: пункты меню по ролям. Гость видит «Карточки врачей». Врач — «Записи», «Запись на приём», «Карточки врачей», «Форма записи». Admin и root — ещё «Добавить врача».
- AC-UI-HEADER-03: гость, открывший закрытую страницу, попадает на `/login`.
- AC-I18N-01: переключение RU/EN/GR меняет все тексты. Выбор сохраняется. По умолчанию RU.
- AC-I18N-02: во всех трёх json, и на фронте, и на бэке, одинаковый набор ключей.
- AC-UI-LOGIN-01: на странице входа есть поле email и кнопки «Авторизоваться» (активна только при корректном email) и «Войти по логину и паролю».
- AC-UI-LOGIN-02: для неизвестного email под полем появляется красный текст ошибки.
- AC-UI-LOGIN-03: при успехе показывается сообщение «Ссылка отправлена на почту».
- AC-UI-LOGIN-04: в режиме логина и пароля поле email скрыто, поля «Логин» и «Пароль» идут друг под другом. «Авторизоваться» активна, когда оба поля заполнены. При ошибке показывается текст ошибки. Кнопка «Войти по email» возвращает к форме с email.
- AC-UI-LOGIN-05: `/auth/magic?token` выполняет вход и переводит на «Записи». Для просроченной ссылки показывается сообщение об ошибке.
- AC-UI-LOGOUT-01: «Выйти» открывает попап «Действительно выйти из системы?» с кнопками «Да» и «Нет». «Нет» закрывает попап. «Да» завершает сессию, в шапке появляется «Войти».
- AC-UI-DP-01: DatePicker показывает сетку месяца, листает месяцы вперёд и назад, выбирает дату, поддерживает `isDateDisabled`, неделя начинается с понедельника, тексты локализованы.
- AC-UI-REC-01: «Записи» — два столбца. Слева список врачей над календарём, по умолчанию «Все». У врача в списке только он сам.
- AC-UI-REC-02: клик по дате показывает справа таблицу. Заголовок — выбранная дата. Колонки: начало–конец, ФИ врача, кабинет, пациент, телефон. Отменённые записи помечены.
- AC-UI-REC-03: если записей нет, показывается «Записей нет».
- AC-UI-REC-04: кнопка «Отменить» есть только при `canCancel`. Она открывает попап подтверждения, после «Да» запись помечается отменённой.
- AC-UI-BOOK-01: «Запись на приём» — слева список активных врачей над календарём. Врачу он сам выбран заранее, и список заблокирован.
- AC-UI-BOOK-02: в календаре недоступны прошедшие дни и нерабочие дни врача.
- AC-UI-BOOK-03: после выбора врача и даты справа появляются время начала (шаг 30 минут), длительность (от 1 часа, шаг 30 минут, до конца свободного окна) и неактивная кнопка «Записать».
- AC-UI-BOOK-04: когда время выбрано, кнопка становится активной. Клик открывает «Форму записи».
- AC-UI-BOOK-05: если свободных окон нет, показывается «Нет свободного времени».
- AC-UI-FORM-01: в форме заранее заполнены и не редактируются ФИ врача, дата и время. Поля: «Имя пациента» и «Телефон» обязательны, «Комментарий» нет. Кнопки «Записать» и «Назад».
- AC-UI-FORM-02: если обязательные поля пусты, показываются ошибки, попап не открывается.
- AC-UI-FORM-03: открывается попап «Подтвердить запись» с кнопками «Да» и «Нет». «Да» сохраняет запись и переводит на «Запись на приём» с сообщением об успехе. «Нет» закрывает попап.
- AC-UI-FORM-04: если слот занят (409), показывается ошибка, пользователь остаётся на форме.
- AC-UI-FORM-05: открытая из меню без выбранного слота форма показывает подсказку и ссылку на «Запись на приём».
- AC-UI-CARDS-01: карточки показываются списком: ФИ, специализация, телефон, email, дни приёма, начало и конец рабочего дня.
- AC-UI-CARDS-02: поле поиска над списком фильтрует по фамилии, имени и специализации при вводе, без учёта регистра, для кириллицы и греческого тоже.
- AC-UI-CARDS-03: иконка «Редактировать» видна только admin и root. Деактивированные карточки и админы (для root) помечены.
- AC-UI-DOC-01: в форме «Добавить врача» над каждым полем есть label. Поля: Фамилия, Имя, Специализация, Телефон, Почта, Кабинет, Приёмные дни (чекбоксы Пн–Вс в ряд), Приёмное время (два прокручиваемых списка 00:00–24:00 с шагом 30 минут), Логин, Пароль. Кнопки «Сохранить» и «Отмена».
- AC-UI-DOC-02: root видит выбор роли. При роли «Администратор» поля врача скрыты.
- AC-UI-DOC-03: проверяются обязательные поля, формат email, выбор хотя бы одного дня и условие «конец позже начала». При ошибках сохранить нельзя.

## Тесты: где и как

- **API-тесты бэкенда** лежат в `tests/api/*.spec.ts` (Jest + supertest). Каждый файл поднимает `createApp` с временной БД, `mail: 'memory'` и управляемыми часами (`now`).
- **Unit-тесты фронтенда** лежат в `tests/frontend/*.spec.tsx` (Jest + jsdom + React Testing Library). Запросы к API мокаются через `jest.spyOn(global, 'fetch')`.
- **E2E** лежат в `tests/e2e/*.spec.ts` (Playwright). В `webServer` запускаются backend с тестовой БД и `SEED_DEV=true` и собранный фронтенд. Mailpit работает в docker на `:8025`, тесты читают через его API письма с magic link и уведомлениями.
- **Именование.** Название теста начинается с AC-ID, например `test('AC-AUTH-04: просроченная ссылка → 401', …)`.

## Проверка

1. `npm run test:api` — после фазы A все тесты красные по правильной причине (404 или неверный ответ, а не ошибка компиляции). После фазы B все зелёные.
2. `npm run test:frontend` и `npm run test:e2e` (Mailpit: `docker compose -f build/docker-compose.yml up mailpit`) — после C красные, после D зелёные.
3. `npm run lint` без ошибок.
4. `build/smoke.sh`: собирает образ, поднимает compose, создаёт запись, пересоздаёт контейнер и проверяет, что запись осталась.
5. Ручная проверка в браузере:
   - войти как `root`/`root1234`;
   - добавить врача, записать пациента и проверить письмо в Mailpit (`localhost:8025`);
   - отменить запись;
   - переключить языки.
6. Результаты тестов сообщаются честно: упавшие и пропущенные тесты называются явно.
