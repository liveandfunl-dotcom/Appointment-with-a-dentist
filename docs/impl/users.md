# Пользователи, роли, карточки и форма врача

Модель данных и миграции, пользователи трёх ролей (root, администратор, врач), API управления ими, страница «Карточки врачей» и форма «Добавить врача» / редактирования.

Статус: реализовано, 2026-11-26. Обзор MVP — [clinic-mvp.md](clinic-mvp.md).

## Что реализовано

- **БД** (SQLite, `node:sqlite`): миграция `1 initial` создаёт `Users`, `Appointments`, `MagicLinks`, `Sessions` и служебную `schema_migrations`. Миграции и сиды выполняются при каждом старте приложения до приёма запросов.
- **Роли.** Роль вычисляется из флагов `isRoot`, `isAdmin`, `isDoctor`; в БД ограничение `CHECK (isAdmin + isDoctor + isRoot = 1)`. В API роль — строка `root` | `admin` | `doctor`.
- **API**: `GET /api/users`, `GET /api/users/:id`, `POST /api/users`, `PATCH /api/users/:id`.
- **Frontend**: `DoctorsPage` (`/doctors`, карточки с поиском) и `DoctorFormPage` (`/doctors/new`, `/doctors/:id/edit`).

## Поведение и решения сверх описания

- **Кто что видит в `GET /api/users`** (маршрут открыт и для гостя): гость и врач — только активных врачей; admin — всех врачей, включая деактивированных (с `isActive`); root — врачей и администраторов (с `role`). Root не показывается никому. Поля `login` и `pass` в списке не отдаются; `GET /api/users/:id` (admin и root) добавляет `login`, пароль не отдаётся никогда.
- **Права на изменение.** Admin управляет только врачами, root — врачами и админами. Создать админа может только root (проверка роли идёт до проверки остальных полей). Root через API не меняется и не создаётся (403 на PATCH). У врача на `POST`/`PATCH` — 403, у гостя — 401.
- **Создание.** Поле `role` (`doctor` | `admin`) обязательно. У админа поля врача (специализация, кабинет, дни, время) игнорируются. У врача обязательны специализация, кабинет (целое ≥ 1), дни (массив 1–7), `workStart` < `workEnd` (формат `HH:mm`, шаг 30 минут, 00:00–24:00). Фамилия и имя — до 100 символов, телефон — до 32.
- **Логин и пароль необязательны**, но только парой: пароль без логина и логин без пароля при создании дают `VALIDATION_ERROR` по полю `password`. Логин: 3–50 символов `[A-Za-z0-9._-]`. Пароль: от 8 символов, не обрезается. Без логина пользователь входит только по magic link. В БД ограничение `pass IS NULL OR login IS NOT NULL`.
- **Редактирование (`PATCH`).** Частичное обновление: меняются только присланные поля. Пустой пароль не меняет текущий. Пустой логин снимает логин и пароль вместе. Если у пользователя нет пароля, а логин задаётся, пароль обязателен. Цель проверяется раньше тела запроса.
- **Уникальность.** Email хранится в нижнем регистре, уникален без учёта регистра (`COLLATE NOCASE`). Занятый email — 409 `EMAIL_TAKEN`, логин — 409 `LOGIN_TAKEN` (если заняты оба, `EMAIL_TAKEN`).
- **Деактивация** (`isActive=false`): пользователь не входит, не получает письма magic link, к нему нельзя записать, его сессии удаляются. `isActive=true` возвращает доступ. Данные и прошлые записи сохраняются.
- **Пароли**: хеш scrypt (см. [auth.md](auth.md)), в ответах API нет.
- **Сиды.** Root (`root` / `root1234`, `root@clinic.local`) создаётся всегда. При `SEED_DEV=true` добавляются 5 врачей (`doctor1`…`doctor5`, пароль `doctor1234`, разные специализации, кабинеты и графики, фамилии на русском, греческом и английском) и администратор (`admin` / `admin1234`). Сид идемпотентен по email: существующий пользователь не изменяется.
- **Frontend, карточки.** Показываются ФИ, специализация, телефон, email, кабинет, дни и часы приёма. Администратор помечен «Администратор», деактивированный — «Деактивирован» (карточка затемнена). У администраторов кабинет, дни и время не показываются. Иконка редактирования (`✎`, ссылка) видна только admin и root. Поиск без учёта регистра по фамилии, имени (в любом порядке) и специализации, работает для кириллицы и греческого (`toLocaleLowerCase`).
- **Frontend, форма.**
  - Выбор роли («Врач» / «Администратор») виден только root; при редактировании он заблокирован. Для роли «Администратор» поля врача скрыты.
  - «Приёмные дни» — чекбоксы Пн–Вс в ряд; «Приёмное время» — два выпадающих списка `<select>` с шагом 30 минут (00:00–24:00), по умолчанию 09:00–17:00.
  - Валидация на клиенте повторяет серверную: обязательные поля, формат email, хотя бы один день, «конец позже начала», пароль не короче 8 символов. Ошибки сервера (`EMAIL_TAKEN`, `LOGIN_TAKEN`, поля из `VALIDATION_ERROR`) показываются у полей.
  - В форме телефон обязателен всегда, а кабинет и специализация — для врача (сервер требует то же).
  - В режиме редактирования форма заполнена данными, есть чекбокс «Деактивировать» и подсказка, что пустой пароль не меняет текущий. После сохранения и по «Отмене» — переход на `/doctors`.
  - Маршруты формы доступны только admin и root; остальные пользователи перенаправляются на `/doctors`, гости — на `/login`.

## Ограничения

- Root не создаётся и не меняется через API и интерфейс; пароль root меняется только заменой хеша в БД (см. [clinic-mvp.md](clinic-mvp.md)).
- Удаления пользователей нет, только деактивация.
- Смена роли существующего пользователя не поддерживается.
- Деактивация врача не отменяет его будущие записи: они остаются активными, но новых записей к нему не создать.
- Все миграции пока одна (`1 initial`); изменения схемы — только новой миграцией, применённые не редактируются.
